# Findings (ranked)

**1. The "parity" gate is real and already wired into CI.** `tests/packs/test_renderer_parity.py` (665 lines) does **not** "hash input JSON and render nothing" as the brief claims. It launches real backends: `test_real_remotion_renders_each_semantic_variant` (:304), `test_real_ffmpeg_renders_supported_semantic_variants` (:339), hybrid (:381, :404), and ffprobe-asserts dimensions/fps/duration (:245–253). The only hashing is `sha256_file(outputs[0]) == sha256_file(outputs[1])` (:469) — output-determinism, not input hashing. Binary media (black.mp4/silence.m4a) is generated at setup (:112–150); none committed (docstring :3–4).

**2. Fixture authority moved out of `tests/`.** `tests/fixtures/sprint08/` is a retired README (:1–24) pointing to `astrid/core/rendering/fixtures/renderer_parity/` (9 files: 6 timeline JSONs, assets, theme-overrides, remotion wrapper) — shipped in the wheel (smoke_wheel_install.sh:92–136). `tests/golden/hype/merged_render_props.json` is the theme golden, asserted at test_renderer_parity.py:280–281.

## Verified facts
Parity gate renders real tiny videos, not hashes; fixtures ship in-wheel; CI/Makefile already run it.

## Unknowns
mp4 byte sizes; whether Remotion tests actually pass on CI (chromium denial path :234–242 suggests mac-only renders are tolerated, not run).

## Risks
A "parity" gate exercising nothing is already avoided — but Remotion assertions can silently early-return on macOS denial (:328–330), so CI could pass without a real Remotion render.

## Suggested approach
Keep the existing lane; add a CI-side assertion that at least one Remotion render completed (no early-return), and pin `merged_render_props.json` drift via a golden-compare test.
