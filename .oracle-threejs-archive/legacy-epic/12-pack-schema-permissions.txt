# Findings (ranked)

**1. `extensions.rendering` already exists — it is the live model, not a new idea.** `astrid/packs/rendering/pack.yaml:42-50` declares `renderers: [backends/remotion/renderer.yaml, backends/ffmpeg/renderer.yaml]`, `planners: [planners/legacy_hybrid/planner.yaml]`, `finalizers: [finalizers/ffmpeg/finalizer.yaml]`. Grep confirms it is the *only* pack using `extensions:`.

**2. Validation/loading pipeline (all four layers already support it):**
- Schema: `astrid/core/pack/schemas/v1/pack.json:108-257` — `extensions` object, `additionalProperties:false` (256); `rendering` block (215-232) allows only string-array `renderers/planners/finalizers` (231).
- Loader: `loader.py:133` → `permissions.py:123-137` (`_optional_pack_extensions`, allowed keys include `rendering`); stored on `PackDefinition.extensions` (`definition.py:47`).
- Consumption: `pack/registry.py:260-303` `pack_rendering_manifest_paths` reads `pack.extensions["rendering"]`, resolves paths against pack root, rejects absolute/traversal escapes (298-301). `rendering/registry.py:528-552` loads them into `RendererRegistry`/`PlannerRegistry`/`FinalizerRegistry` per discovered pack.

**3. Permissions are pack-wide, unscoped.** pack.yaml:12-18 declares `subprocess`, `project_files`, `network` ("Sprite sheet executor calls OpenAI GPT Image API") — the network grant applies to every executor in the pack, including `rendering.render`, whose own isolation is `subprocess` + `network:false` (executor.yaml:149-154). No per-feature/per-executor scoping exists in the pack manifest.

**4. pack.yaml discovery:** `discovery.py:79-164` (layers source/local/extra/env/installed → `DiscoveredPack`). Manifest filenames per kind live in `pack/_common.py:16-25` (`EXECUTOR_MANIFEST_NAMES = ("executor.yaml","executor.yml","executor.json")`, etc., in `_COMPONENT_MANIFEST_NAMES`; `find_component_manifest` 28-39). `PackAliasKind` already includes `renderer/planner/finalizer` (`_common.py:40-47`) — but renderer.yaml is **not** filename-discovered; it's extension-declared.

**5. executor.yaml → CapabilityRegistry:** `walkers.py:23-27` (`iter_executor_roots` via `content.executors`) → `execution/executor/folder.py:45-78` → id validated to pack (`registry.py:310` `validate_content_id_in_pack`) → `_attach_pack_metadata` (311) → `CapabilityRegistry` (imported `registry.py:34`). Qualified id `rendering.render` comes from the manifest's own `id` field (executor.yaml:89).

# Verified facts
- pack.yaml: `content: {executors: executors, elements: elements}`; permissions subprocess/project_files/network; `extensions.rendering` with 3 path lists.
- executor.yaml inputs: timeline (file, required), assets_registry (file, opt), theme (file, opt), engine/backend (string, mutually exclusive per description only), backend_config (json), output_name (string, default hype.mp4), keep_previous_renders (boolean).

# Unknowns
- Whether executor `isolation.network:false` overrides pack-wide `network` at runtime (permission→isolation flow not traced).
- `RendererManifest`/`PlannerManifest`/`FinalizerManifest` schema location (in rendering registry, not pack schema).
- Engine flag constraints are description-only; no schema-level mutual exclusion.

# Risks
- `additionalProperties:false` at both schema (pack.json:256, 231) and loader (permissions.py:135-137) — new sub-keys silently rejected unless both are updated.
- `validate.py:560` validates rendering manifest paths; traversal guard (registry.py:298-301) forces pack-root-relative paths.
- Pack-wide `network` permission would bless any new renderer feature unless scoping is added.

# Suggested approach
Extend the existing `extensions.rendering` block (schema + `_optional_pack_extensions` normalization + rendering registry consumers); keep paths pack-relative; add per-feature permission scoping (e.g., `access`/`services` on permissions entries) so sprite-sheet network does not leak to rendering.
