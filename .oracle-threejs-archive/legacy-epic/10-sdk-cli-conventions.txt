## Ranked findings

**1. SDK export is lazy and test-pinned.** `astrid/__init__.py:7-51` defines `_SDK_EXPORTS` + module-level `__getattr__`; `import astrid` never imports `astrid.sdk`. `tests/test_sdk_public_surface.py:99-109` runs a fresh subprocess asserting `tuple(astrid.__all__) == EXPECTED_PUBLIC_NAMES` (from `tests/_sdk_contract.py`), `astrid.sdk` not in `sys.modules`, and no heavy execution modules loaded. Any new public name must be added to `_SDK_EXPORTS` **and** `EXPECTED_PUBLIC_NAMES` (exact-tuple equality).

**2. SDK module pattern.** `sdk/generation.py`: module-level helpers + `@dataclass(frozen=True) GenerationFacade` (`:141`), lazy heavy imports inside functions (`:30,:128,:153`), `__getattr__` plugin-verb fallback (`:151`), singleton `generate = GenerationFacade()` (`:331`). `sdk/results.py:59-142`: frozen DTOs (`Capability`, `DiscoveryResult`, `InvocationResult`) with `to_dict()` via `_json_safe_mapping`; no pydantic anywhere. `sdk/dto.py` re-exports core contracts. `sdk/rendering.py` already exists (render, `renderer_main`, support; exported at `__init__.py:12-14`).

**3. `astrid renderers` already exists.** `dispatch.py:423-466` `_TOP_LEVEL_HANDLERS` dict includes `"renderers": _dispatch_renderers` (`:454`, handler `:315` → `astrid.core.rendering.cli.main`); help text at `gateway/help.py:92-93`; unbound allowlist `("renderers",)` at `gateway/__init__.py:167` (gate table `:149-172` — "do not add ad hoc unbound exceptions outside this tuple"). CLI verbs: create/list/inspect/validate/smoke/support/replay (`rendering/cli.py:7-20`). No `--engine` flag in rendering CLI → no collision with lifecycle `--engine task|arnold` (`dispatch.py:17,107-145`).

**4. JSON conventions.** rendering CLI explicitly uses **verb-specific shapes, never a universal envelope** (`rendering/cli.py:22-25`); exit codes 2/1/130 (`:44-46`). Contrast: `executors list --json` → `{"executors": [...]}` with `_capability`/`source_pack` keys (`cli_handlers.py:185-193`).

**5. Modality collision.** `core/modalities/__init__.py:12` `_RENDERERS` = output-kind hint modules (`renderer_ids()`, `list_renderers()`); `modalities list --json` emits `{"renderers": [...]}` (`:59`). Iteration_video uses `renderer: str = "remotion"` value (`plan_template.py:26`). Separate namespaces, but "renderers" already denotes modality hints in `--json` payloads.

## Verified facts
- Lazy `__getattr__` export mechanism with exact-tuple test pinning.
- `renderers` verb, unbound gate, help, and SDK rendering exports already shipped.
- Frozen-dataclass DTO convention; no pydantic.

## Unknowns
- Whether epic's "add `astrid renderers`" predates this scaffold (it appears done); what `renderers list --json` shape is vs. modality `{"renderers":[...]}`.
- `EXPECTED_PUBLIC_NAMES` current contents for render-related names.

## Risks
- Adding SDK names breaks `test_import_astrid_exposes_exact_curated_sdk_names` (tuple equality).
- Modality `{"renderers":[...]}` JSON vs. renderers-CLI JSON ambiguity.
- `--engine` values (task|arnold) if renderers CLI ever adds `--engine` (currently absent).

## Suggested approach
Extend the existing `rendering/cli.py` family (already wired end-to-end), mirror `generation.py` facade pattern for a renderer SDK, and update `_SDK_EXPORTS` + `EXPECTED_PUBLIC_NAMES` together with a surface test.
